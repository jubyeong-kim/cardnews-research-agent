# 00 · 총괄 — 전체 지도와 계약

이 문서는 **여섯 담당이 서로 뭘 주고받는지**만 정한다. 각 담당이 안에서 어떻게
만드는지는 각자 문서에 있다. 여기서 정한 계약을 어기면 옆 담당이 깨진다.

읽는 순서: **이 문서 → 자기 번호 문서**. 자기 문서만 읽고 시작하지 말 것.

---

## 왜 만드나

캐리어 플랫폼 사업의 SNS 계정을 돌린다. 매번 손으로 자료 찾고 카드뉴스 원고
쓰는 건 지속이 안 된다. **사람이 판단할 자리는 남기고 나머지를 자동화한다.**

원본 요구사항은 `card-news-workflow-kit/PRD.md` 에 있다. 그 문서가 요구하는
핵심은 "원고 생성기" 가 아니라 **사용자 답변에 따라 다음 행동이 바뀌는 흐름**
이다. 그래서 흐름을 코드에 숨기지 않고 n8n 노드로 눈에 보이게 둔다.

---

## 전체 흐름

```
 [사람] 주제 입력
     │
     ▼
 ┌─────────────────────────────────────────┐
 │ 조사 단계 (이미 있음 · cardnewsMvp0001)  │
 │  조사 → 후보 선택 → 심층조사 → 승인       │   ← 사람이 두 번 개입
 └─────────────────────────────────────────┘
     │  runs/<runId>/storyboard.json
     ├──────────────────────────┐
     ▼                          ▼
 ┌──────────┐             ┌──────────┐
 │ 01 제작   │             │ 03 자료축적│ ← 품목·출처를 표로 쌓음
 └──────────┘             └──────────┘
     │ cards/*.png              ▲
     ▼                          │
 ┌──────────┐                   │
 │ 05 업로드 │ (사람 확인 후)     │
 └──────────┘                   │
     │ publish.json             │
     ▼                          │
 ┌──────────┐   성과 데이터       │
 │ 02 반응수집├───────────────────┘
 └──────────┘        │
                     ▼
                ┌──────────┐
                │ 04 유행조사│ → 다음 기획에 반영
                └──────────┘
```

| 번호 | 담당 | 소유하는 것 | 도는 주기 |
|---|---|---|---|
| — | **조사** (이미 있음) | 주제 → 승인된 스토리보드 | 카드뉴스 만들 때 (폼 제출) |
| 01 | **제작** | 스토리보드 → 카드 이미지 | 승인 직후 |
| 02 | **반응 수집** | 게시물 → 성과 숫자 | 매일 |
| 03 | **자료 축적** | 모든 실행 → 조회 가능한 표 | 실행 끝날 때마다 |
| 04 | **유행 조사** | 성과 데이터 → 기획 지침 | 주 1회 |
| 05 | **자동 업로드** | 카드 → 실제 게시 | 예약 시각 |

**개발 순서는 01 → 02 → 03 → 04 → 05.** 번호가 곧 순서다. 근거는 각 문서
맨 위에 적었다. 05 를 마지막에 두는 이유는 기술이 어려워서가 아니라 **되돌릴
수 없는 동작**이기 때문이다.

## 폴더를 따로 두지 않는다

**한 저장소, 한 n8n 인스턴스로 간다.** 담당별로 저장소를 쪼개자는 제안이
있었는데 하지 않는다. 이유:

1. **주고받는 것이 파일이다.** 계약이 `runs/<runId>/` 폴더다. 같은 디스크에
   있으면 계약 확인이 `ls` 한 번이다. 저장소를 쪼개면 그게 연동 문제가 된다.
2. **공유하는 게 많다.** n8n credential(키 3개), `scripts/ask-claude.ps1`,
   `scripts/find-n8n.ps1`, `deploy.ps1`, 빌드 방식(`tools/build_*.py`)을 전부
   같이 쓴다. 쪼개면 이걸 다섯 벌 관리한다.
3. **혼자 만든다.** 사람이 여럿이면 소유권 분리가 값을 하지만, 지금은 맞춰야
   할 곳만 늘어난다.

대신 **이것들은 담당별로 나눈다:**

```
n8n/
├─ agents/               ← 이 문서들. 담당당 1개
│   00-총괄.md  01-제작.md  02-반응수집.md
│   03-자료축적.md  04-유행조사.md  05-자동업로드.md
├─ tools/                ← 빌더도 담당당 1개
│   build_wf.py          (조사 · 이미 있음)
│   build_make.py        (01 이 만들 것)
│   build_metrics.py     (02)
│   …
├─ workflows/            ← n8n 워크플로 JSON. 담당당 1개, id 도 따로
├─ scripts/              ← 공용
├─ runs/<runId>/         ← 계약. 아래 참조
└─ library/              ← 03 이 소유하는 누적 데이터
```

**워크플로는 반드시 나눈다.** 주기가 다르기 때문이다 — 폼 제출로 도는 것과
매일 도는 것을 한 워크플로에 넣으면 둘 다 이상해진다.

## 계약 · `runs/<runId>/`

`runId` 는 **조사 워크플로의 n8n 실행 번호**다 (`$execution.id`). 숫자 하나이고
전 담당이 이걸로 같은 건을 가리킨다.

```
runs/46/
├─ storyboard.json        [조사가 씀]  승인된 카드 구조. 01 의 입력
├─ script.md              [조사가 씀]  사람이 읽는 원고
├─ sources.md             [조사가 씀]  출처·근거 등급 정리
├─ items-checked.json     [조사가 씀]  품목별 원문 대조 판정
├─ product-shots.json     [조사가 씀]  제품컷 후보 (권리 미해결)
├─ source-text.txt        [조사가 씀]  실제로 가져온 원문 전문
├─ cards/                 [01 이 씀]
│    01.png … 07.png
│    manifest.json          카드별 크기·해시·생성 시각
├─ publish.json           [05 가 씀]   게시 시각·계정·게시물 id
└─ metrics/               [02 가 씀]
     2026-09-12.json        그날 읽은 성과 숫자
```

**규칙 넷:**

1. **자기 것만 쓴다.** 남이 쓴 파일은 읽기만 한다. 위 표의 `[누가 씀]` 이
   그 파일의 유일한 작성자다.
2. **없으면 아직 안 된 것이다.** 별도 상태 파일을 두지 않는다. `cards/` 가
   없으면 제작 전, `publish.json` 이 없으면 미게시다.
3. **덮어쓰지 말고 더한다.** `metrics/` 는 날짜별 파일을 쌓는다. 지난 숫자를
   덮으면 추이가 사라진다.
4. **읽는 쪽은 없을 때를 처리한다.** 앞 단계가 실패해도 뒷 단계가 터지지
   않아야 한다. 지금 조사 워크플로가 그렇게 돼 있다 — 유튜브가 죽어도 웹으로
   간다.

### `storyboard.json` 모양 (01 이 쓰는 입력)

```json
{
  "audience": "캐리어 플랫폼 인스타 - 여행 준비하는 20~30대",
  "angle": "…한 줄 편집 방향…",
  "hooks": ["후킹 문구 후보", "…"],
  "items": [{
    "name": "고베 푸딩",
    "from": "c8",
    "itemType": "제품 | 장소",
    "evidence": "official | confirmed | weak | retail_only | unconfirmed",
    "affiliate": false,
    "query_used": "실제로 쓴 검색어",
    "sources": ["https://…"]
  }],
  "cards": [{
    "no": 1,
    "role": "표지 | 본문 | 마무리",
    "title": "…",
    "body": "…",
    "source": "확인한 URL | 미확인 | 해당 없음",
    "image_plan": "구도·분위기·색과 글자 넣을 빈 공간"
  }]
}
```

`items` 와 `cards` 는 **따로다.** 카드 수와 품목 수가 같지 않다(표지·마무리는
품목이 없다). 품목을 보려면 `items`, 화면을 그리려면 `cards` 를 본다.

## 전 담당 공통 규칙

이건 협상 대상이 아니다. 여기서 정하고 각 문서에서 반복하지 않는다.

### 키

**API 키 값을 저장소·대화·로그·워크플로 JSON 에 절대 넣지 않는다.** 키는
n8n Credentials 에만 산다. `workflows/*.json` 은 credential 이 비어 있는
템플릿이고, `deploy.ps1` 이 DB 사본에서 키를 이어붙인다.

`.gitignore` 가 `*.sqlite`, `*-with-creds.json`, `mvp-from-db.json`,
`runs/*` 를 막고 있다. 새 담당이 키가 박히는 중간 파일을 만들면 여기 추가할 것.

**credential 은 인증 방식이 아니라 호스트로 맞춘다.** Tavily 와 Gemini 가 둘 다
Header Auth 라서, 인증 방식만 보고 고르면 Tavily 키가 구글로 나간다. 실제로 한
번 그럴 뻔했다 (`DECISIONS.md` 참조). `tools/reapply.py` 가 호스트로 맞추고,
모르면 비운 채 경고한다. **경고가 나오면 n8n UI 에서 직접 고를 것.**

### 저작권

- **정보는 가져와도 된다.** 저작권은 표현을 보호하지 사실을 보호하지 않는다.
  여러 출처를 교차 확인하고 우리 문장으로 새로 쓰는 지금 구조는 문제없다.
- **피할 것 둘:** ① 한 출처의 선택·배열을 그대로 옮기는 것 (그래서 후보를
  2~3개 고른다) ② 문장을 베끼는 것.
- **남의 사진은 쓰지 않는다.** 누끼를 따도 2차적저작물작성권은 원저작자에게
  있다(저작권법 제22조). `product-shots.json` 은 **권리가 해결된 사진이
  아니라 찾는 수고를 줄인 후보 목록**이다. 쓰려면 출처 페이지에서 조건을
  직접 확인해야 한다.
- 안전한 순서: **제조사 공식 제품컷 → 직접 촬영 → 유튜버 허락 → 사진 없이
  타이포**. 당분간은 마지막이다.

### 근거

원고에 쓰는 주장은 등급이 붙는다.

| 등급 | 뜻 | 카드에 쓸 수 있나 |
|---|---|---|
| `official` | 관광국·지자체·브랜드 공식 | 단언 가능 |
| `confirmed` | 서로 다른 출처 2곳 이상 | 단언 가능 |
| `weak` | 그런 출처 1곳 | **어디서 나온 말인지 밝혀서** 쓸 것 |
| `retail_only` | 쇼핑몰 상품페이지만 | 추천 근거로 쓰지 말 것 |
| `unconfirmed` | 못 찾음 | 쓰지 말 것 |

그리고 **원문 대조** 가 따로 돈다 — 품목명이 우리가 실제로 가져온 원문에
글자 그대로 있는지 본다.

| 판정 | 뜻 |
|---|---|
| `in_source` | 원문에 그대로 있음 |
| `head_only` | 괄호 앞만 있음 (괄호 안은 모델 추측 가능성) |
| `parts_in_source` | 단어는 전부 있으나 이 이름 그대로는 없음 (모델이 조합) |
| `not_in_source` | 없음 — **카드에 쓰지 말 것** |
| `no_source` | 원문을 못 가져와 대조 불가 |

두 축은 **다른 것을 본다.** 등급은 "출처가 믿을 만한가", 원문 대조는 "우리가
지어낸 건 아닌가". 둘 다 봐야 한다.

### 되돌릴 수 없는 동작

**사람 확인 없이 공개로 나가는 동작을 만들지 않는다.** 게시·삭제·DM 은 전부
승인 뒤에만. 지금 조사 워크플로의 승인 화면이 그 방어선이고, 05 가 두 번째
방어선을 하나 더 둔다.

### 실패했을 때

- **조용히 실패하지 않는다.** 삼키지 말고 화면이나 파일에 이유를 남긴다.
  이전에 래퍼가 진짜 오류를 감춰서 "근거가 전부 미확인" 으로만 보인 적이 있다.
- **한 소스가 죽어도 나머지로 간다.** HTTP 노드는
  `onError: continueRegularOutput` + 재시도를 붙이고, 읽는 쪽이 빈 값을
  처리한다.
- **기다림에는 반드시 상한과 보고가 있다.** 무한 대기 금지. 시간이 지나면
  성공이든 실패든 말한다.

## 이미 있는 것 — 조사 단계

새로 만들지 말 것. 이미 돌고 있다.

| | |
|---|---|
| 워크플로 | `cardnewsMvp0001` · 노드 29개 |
| 소스 | `tools/build_wf.py` (**유일한 편집 지점**) |
| 폼 | http://localhost:5678/form/cardnews-start-form |
| 배포 | `powershell -File deploy.ps1` |

**n8n UI 에서 고치지 말 것.** `build_wf.py` 를 고치고 `deploy.ps1` 을 돌린다.
UI 수정은 다음 배포에 덮인다. 반대로 **credential 연결만은 UI 에서** 한다 —
그건 DB 에만 있고 템플릿에는 없다.

`build_wf.py` 는 쓰기 전에 두 가지를 검사한다. 통과 못 하면 파일을 안 쓴다.
- Code 노드 전부 `node --check`
- 원문 대조 판정 규칙을 fixture 8건으로

새 빌더를 만들 때 이 습관을 가져갈 것. 이 검사가 실제 오류를 여러 번 잡았다.

### 쓰는 외부 서비스와 한도

| 서비스 | 쓰는 곳 | 무료 한도 | 실측 |
|---|---|---|---|
| YouTube Data API v3 | 영상 후보·설명 전문 | `search.list` 하루 100회 전용 버킷 | 카드뉴스 1건에 1회 |
| Tavily | 웹 후보·본문 추출·제품컷 | 월 1,000 크레딧 | 1건에 몇 크레딧 |
| Gemini (AI Studio) | 유튜브 영상 분석 | RPM 5 / TPM 250K / **RPD 20** | 17분 영상 = 입력 105K |
| Claude CLI | 평가·심층조사·스토리보드 | 세션 한도 | 1건에 2~4회 |

**제일 먼저 걸리는 건 Gemini RPD 20 이다.** 영상 3편이면 하루 6회 실행이
한계다. 모델마다 따로 잡히므로 `gemini-3.7-flash` 로 바꾸면 20회가 더 생긴다.
남은 양: https://aistudio.google.com/rate-limit

**새 담당은 한도를 쓰기 전에 이 표를 갱신할 것.** 넷이 같은 키를 나눠 쓴다.

## 아직 안 정한 것

담당이 정하지 말고 **여기서 결정한 뒤 각자 반영**할 것. 각자 정하면 어긋난다.

- **카드 규격.** 1080×1350 (4:5) 로 갈 것인가. 01 과 05 가 같이 영향받는다.
- **브랜드.** 색·서체·로고가 아직 없다. 01 이 첫 시안을 내고 사람이 고른다.
- **인스타 계정 형태.** 비즈니스 계정 + 페이지 연결이 있어야 02·05 가 산다.
  아직 확인 안 됐다.
- **본문 길이.** 실행 46 의 카드 본문이 130~180자였다. 인스타 카드에 얹기엔
  길다. 줄이는 건 **디자인이 아니라 원고 단계**가 할 일이므로, 정해지면
  `build_wf.py` 의 스토리보드 프롬프트에 상한을 넣는다.
- **보관 기간.** `runs/` 가 실행마다 쌓인다. 언제 지울지 안 정했다.

## 지금 상태

여러 개 고른 경우는 아직 실키로 확인 못 했다** — 영상 1편만 걸렸다. 01 을
시작하기 전에 그 한 번을 돌려 `storyboard.json` 모양을 굳히는 게 좋다.
