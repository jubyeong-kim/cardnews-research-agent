# 02 · 반응 수집 — 올린 게 실제로 먹혔는지

> 먼저 `00-총괄.md` 를 읽을 것.

## 왜 두 번째인가

지금 이 시스템에는 **잘했는지 못했는지 알려 주는 입력이 하나도 없다.** 근거를
따지고 원문을 대조하고 교차 확인까지 하는데, 정작 그렇게 만든 카드뉴스가
먹혔는지는 모른다.

03(자료 축적)·04(유행 조사)는 **이 데이터가 있어야 값을 한다.** 성과 없이
쌓기만 하면 그냥 창고고, 성과 없이 유행을 조사하면 남의 얘기다.

그리고 **읽기만 한다.** 되돌릴 수 없는 동작이 없어서 05 보다 먼저 만들어도
안전하다.

---

## 무엇을 소유하는가

`runs/<runId>/publish.json` (05 가 남긴 게시물 id) → `runs/<runId>/metrics/*.json`

게시물이 어떻게 됐는지 매일 읽어서 날짜별로 쌓는다.

## 소유하지 않는 것

- **게시** — 05 소유. 여기는 절대 쓰지 않는다. 읽기 전용 담당이다.
- **해석** — 04 소유. 여기는 숫자를 정확히 가져오는 것까지다. "그래서 뭘
  바꿔야 하나" 는 04 가 답한다.
- **댓글 응답** — 아무도 안 한다. 사람이 한다.

---

## 입력

```json
// runs/46/publish.json  ← 05 가 씀
{
  "platform": "instagram",
  "accountId": "…",
  "mediaId": "1784…",          // 성과 조회의 열쇠
  "permalink": "https://www.instagram.com/p/…",
  "publishedAt": "2026-09-12T19:00:00+09:00",
  "cards": 7
}
```

**`publish.json` 이 없으면 아무것도 하지 않는다.** 미게시 건이다.

05 가 아직 없는 동안은 **사람이 손으로 올리고 이 파일을 직접 만든다.** 그게
02 를 05 보다 먼저 만들 수 있는 이유다. `permalink` 만 있으면 `mediaId` 는
API 로 찾을 수 있다.

---

## 출력

```
runs/46/metrics/
  2026-09-12.json
  2026-09-13.json
  …
```

```json
{
  "runId": "46",
  "mediaId": "1784…",
  "readAt": "2026-09-13T09:00:00+09:00",
  "daysSincePublish": 1,
  "metrics": {
    "reach": 1240, "impressions": 1580,
    "likes": 86, "comments": 4, "saves": 31, "shares": 7,
    "profileVisits": 12, "follows": 2
  },
  "raw": { }
}
```

**규칙:**
- **날짜별로 쌓는다. 덮지 않는다.** 추이가 데이터의 절반이다. "첫날 100,
  일주일 뒤 800" 과 "첫날 800" 은 완전히 다른 얘기다.
- **`raw` 에 응답 원본을 남긴다.** 나중에 다른 지표가 필요해질 때 다시
  못 읽는다 — 인스타 인사이트는 과거를 소급해서 주지 않는다.
- **못 읽은 지표는 넣지 않는다.** 0 으로 채우지 말 것. 없는 것과 0 은 다르다.

---

## 알아야 할 제약

직접 확인하고 이 표를 채울 것. 아래는 **아직 검증 안 된 사전 조사**다.

| 항목 | 알려진 것 | 확인 필요 |
|---|---|---|
| 계정 형태 | **비즈니스/크리에이터 계정 + 페이스북 페이지 연결**이 있어야 인사이트 API 가 열린다 | 지금 계정이 그런가 |
| API | Instagram Graph API (`/{ig-media-id}/insights`) | 실제 응답 필드 |
| 지표 | 게시물 종류(단일/캐러셀/릴스)마다 주는 지표가 다르다 | 캐러셀에서 뭐가 오는가 |
| 보관 | 인사이트는 무한 소급되지 않는다 | 며칠까지 되는가 |
| 앱 심사 | 일부 권한은 심사가 필요하다 | 인사이트 읽기가 해당되는가 |

**`saves`(저장수)가 카드뉴스에서 제일 중요한 지표일 가능성이 높다.** 좋아요는
스쳐 지나가며 누르고, 저장은 "나중에 쓰겠다" 는 뜻이다. 여행 기념품처럼
**나중에 쓰는 정보**는 저장이 진짜 반응이다. 다만 이건 가설이고, 데이터가
쌓이면 04 가 확인한다.

### 키

인스타 토큰도 **n8n Credentials 에만** 넣는다. 총괄의 키 규칙 그대로다.
장기 토큰도 만료되므로 **만료 시 무엇이 보이는지** 확인하고 그때 조용히
실패하지 않게 할 것.

---

## 만드는 순서

1. **계정 형태부터 확인.** 비즈니스 계정 + 페이지 연결이 안 돼 있으면 여기서
   막힌다. 코드 짜기 전에 확인할 것.
2. **손으로 한 번 호출.** curl 로 게시물 하나의 인사이트를 읽어 실제 응답을
   본다. 캐러셀에서 어떤 필드가 오는지 문서만 보고 믿지 말 것.
3. **`publish.json` 을 손으로 만들어** 게시물 하나에 대해 돌려 본다.
4. **매일 도는 워크플로.** n8n Schedule Trigger. `runs/*/publish.json` 을
   훑어 게시 후 N일 이내인 건만 읽는다.
5. 얼마나 오래 추적할지 정한다. 30일쯤이 무난해 보이지만 근거는 없다.

**워크플로 분리:** 이건 조사 워크플로와 주기가 완전히 다르다. 별도 워크플로
id 로 만들고 `tools/build_metrics.py` 로 생성한다.

---

## 하지 말 것

- **쓰기 동작 금지.** 게시·삭제·댓글·좋아요 전부. 이 담당은 읽기 전용이다.
- **매 시간 긁지 말 것.** 하루 한 번이면 충분하고, API 한도는 05 와 나눠 쓴다.
- **0 으로 채우지 말 것.** 위 참조.
- **숫자를 해석하지 말 것.** "이 카드가 좋았다" 는 판단은 04 가 한다.

---

## 완료 판정

1. 게시물 하나에 대해 `metrics/<날짜>.json` 이 매일 하나씩 쌓인다
2. 게시 후 여러 날치가 모여 **추이를 볼 수 있다**
3. 토큰이 만료되거나 게시물이 지워졌을 때 **이유가 보이는 곳에 남는다**
4. `publish.json` 이 없는 실행은 조용히 건너뛴다 (오류 아님)

## 지금 막혀 있는 것

**인스타 계정이 비즈니스 계정인지, 페이스북 페이지에 연결돼 있는지 확인이
안 됐다.** 이게 아니면 이 담당 전체가 불가능하다. 사람에게 먼저 물을 것.
